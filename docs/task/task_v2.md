## 开题背景与意义

**DiceCraft — 基于多Agent的桌游创作与游玩平台**

### 现有问题

**第一层：纯对话系统的局限**

当用户尝试用普通对话系统构建一个结构化的桌游场景时，所有信息挤在同一个上下文中——规则、角色设定、玩家状态、隐藏信息全部平铺。对话越长，上下文越混乱，系统越容易遗忘或混淆早期设定。更根本的问题是，纯对话无法维持游戏运行所需的隐藏状态：所有"内部信息"对用户完全可见，无法实现真正的信息隔离。

**第二层：简单Agent系统的局限**

一些方案引入了Agent框架，通过tool call实现角色切换、状态管理等基础功能。但这些系统的游戏内容仍然是**开发者预设的固定模板**——角色是写死的标签、规则是硬编码的流程、玩法是固定的几种。换一个背景色容易，但想加入需要代码支撑的机制——比如自定义的技能结算逻辑、动态计分规则、条件触发的剧情分支——就只能等开发者手动编写新的prompt和规则代码。Agent在这里只是执行者，不是创造者。

**第三层：自然语言构建的需求**

真正的桌游创作不应依赖固定标签和预设代码。用户用自然语言描述构思，系统应能理解意图并生成完整的可运行游戏——规则、角色、线索、隐藏信息、游戏流程、计算逻辑，全部由Agent协作完成。单一Agent难以独立胜任：构建过程中会产生大量中间状态、失败的探索尝试、以及需要反复查阅资料验证的环节，这些都会迅速拉长上下文导致模型性能退化，因此需要Subagent来分担细节任务、执行探索和进行上下文Compact。此外，游戏构建对代码和逻辑判断的准确性、工具调用的可靠性有较高要求，不同模型在这些维度上表现不一；而生成者天然会被自己的上下文带偏，需要一个脱离该上下文的独立审查者来发现遗漏的问题。

### 我们的方案

**DiceCraft** 是一个桌游创作与游玩平台，重心在"**造**"：玩家用自然语言描述游戏构思，多个Agent协作完成构建、审查、运行的全流程。

## 多Agent架构

本项目的多Agent架构，在构建这一侧，参照OpenCode的Primary Agent + Subagent模式。多Agent不是为了"多"而多，而是每个Agent解决一个单Agent无法可靠完成的问题，然后主要由一个Primary Agent统筹全局，按需派发Subagent处理细节任务，大多数时候Primary只需接收Subagent的结果，避免上下文过长导致性能退化。

而在运行这一侧，GM Agent作为游戏管理核心，负责全局状态和玩家交互，NPC Subagent独立运行，拥有各自的知识范围和性格设定，实现信息隔离。他们之间可以有实时的交互、“私聊”，主要按照角色来划分agent的职责和信息范围，保证游戏运行时的沉浸感和合理性。
### 构建阶段

**Primary Build Agent** 是构建阶段的核心，负责理解用户意图、规划游戏结构、生成完整的游戏方案（规则、角色、线索、隐藏信息、游戏流程）。它可按需派发以下Subagent：

- **Explore Subagent**（可选）：只读的通用探索工具，比直接调用Search更强大。可以在已有项目文件中搜索和理解内容，也可以检索外部知识（历史背景、文化细节、地理信息等），最终以精炼的语言将有效信息返回给Primary，节约Primary的上下文窗口。
- **General Subagent**（可选）：高级任务执行者，用于节约Primary的上下文窗口。将具体的细节操作（编写游戏逻辑脚本、计算数值平衡、生成结构化数据文件等）交给General处理，Primary只需接收结果。支持fork（独立执行，结果回传）和spawn（在隔离环境中执行复杂任务）两种模式。
- **Review Subagent**：构建流程的最后一步。关键设计：**脱离Primary的上下文，在干净的上下文中重新审查**。研究表明LLM容易被自身上下文中的先入之见带偏——即使同一个模型，在干净上下文中作为独立审查者，也更容易发现Primary遗漏的逻辑矛盾、信息泄露风险、角色平衡性问题。

### 运行阶段

- **GM Agent**：掌握全局状态的游戏管理核心。在需要主持人的游戏（如剧本杀、海龟汤）中担任主持人角色；在不需要主持人的游戏（如狼人杀自由发言模式）中负责检查各玩家之间的胜负条件、计分结算等。此外处理玩家的高级指令：退出游玩、热更新游戏规则、切换回编辑模式重新构建等。
- **NPC Subagent**（多个，按需派发）：每个NPC作为独立Subagent运行，拥有各自的知识范围和性格设定。玩家与NPC交互时，GM Agent派发对应的NPC Subagent处理，NPC基于自己的知识和立场生成回应，不知道其他NPC的私有信息。信息隔离由Agent架构保证——不同NPC运行在独立的上下文中。

## Skill与游戏内容

游戏中的具体机制通过Skill系统实现。Skill定义可复用的游戏机制（问答、投票、搜证、技能释放等），提供了通过Bash/Python等方式调用工具的设计模式——比如一个"骰子掷点"Skill内部可能是一个Python脚本处理概率计算并返回结果。Build Agent在构建阶段编写或组合Skill，运行时由GM Agent调用执行。

## 上下文系统

**记忆管理**：不采用传统的RAG向量检索方案，而是由Agent自主管理结构化的记忆文件。游戏方案以分类文件存储（规则文件、角色文件、线索文件、状态文件等），Agent通过文件读写操作管理游戏知识。NPC Subagent启动时仅加载自己应知的文件子集，实现信息隔离。运行过程中的游戏状态变化由GM Agent更新到对应的状态文件中。

**消息可见性**：部分桌游中某些对话只能被特定玩家知晓（如密室私聊、角色专属剧情）。GM Agent控制每条消息的可见范围，将消息分发到对应Agent的上下文中，未授权的Agent不会收到这些内容。

**持久化记忆**：跨局游戏的长期记忆——记录玩家偏好、历史游戏中的角色表现、常用规则修改等，供后续游戏构建和运行时参考。

**Compact系统**：随着游戏进行，Agent上下文会不断增长。Compact机制定期压缩历史上下文，保留关键信息（当前游戏状态、重要决策、未完成的线索），丢弃已过时的细节，确保Agent在长对话中不会因上下文溢出而丢失关键状态。

## 工具集

| 工具 | 用途 |
|------|------|
| **Web Search** | 搜索外部知识（历史背景、文化常识等），供Explore Subagent和GM Agent使用 |
| **Multimodal Understanding** | 多模态理解能力，处理场景图片、玩家动作截图等视觉输入 |
| **TTS** | 语音合成，为不同NPC生成不同音色的语音回应 |
| **Code Execution** | 沙箱执行Python脚本，运行游戏逻辑和数值计算 |

## 项目目标

1. **游戏构建系统**：实现Primary Build Agent + Explore/General/Review Subagent的构建流程，支持自然语言输入生成完整可运行的桌游方案
2. **游戏运行系统**：实现GM Agent主持 + NPC Subagent独立运行的游玩架构，信息隔离由Agent上下文隔离保证
3. **可扩展的游戏内容**：通过Skill系统定义游戏机制，通过脚本处理计分和数值计算
4. **多模态交互**：支持语音合成（TTS）、多模态理解（场景图片/动作识别），提升沉浸感

## 开发技术路线

- **前端**：Web端交互界面（React），2D虚拟桌游屋场景
- **后端**：多Agent调度框架，参照OpenCode的Primary Agent + Subagent架构设计，Agent间上下文隔离
- **AI模型**：MiMo/DeepSeek等开源模型 + MiMo TTS语音合成
- **游戏内容**：Skill系统 + Python脚本执行引擎
- **上下文系统**：记忆管理 + 消息可见性 + 持久化记忆 + Compact机制

后续将支持多人在线交互，当前阶段聚焦单用户与多Agent的交互体验。
